# 融合架构

## 设计边界

项目把两套来源工程迁入同一个 Git 仓库和 Maven Reactor。电商服务继续按用户、商品、购物车、交易、支付拆分；点评业务作为 `local-life-service` 保留其商户、内容、关系链、优惠券和 Redis 缓存模型。旧 `hm-service` 单体不再作为运行模块，以免与拆分后的电商服务重复。

融合点选在共享入口和身份：Gateway 统一提供路由与 JWT 校验，`user-service` 是唯一用户主数据服务，`hm-api` 声明跨服务用户资料契约，`hm-common` 管理用户上下文和公共基础能力。点评的用户相关接口改为依赖共享身份和 Feign 用户资料，不保留第二套用户表、登录态或用户 ID 生成逻辑。

## 请求身份流

1. 用户从 `/users/login` 登录，统一用户服务验证账号密码，或验证 Redis 中的开发验证码并签发 JWT。
2. Gateway 对受保护请求校验 JWT，从 token 提取用户 ID，并把可信用户身份写入下游请求头。
3. 各服务的公共拦截器把请求头中的用户 ID 放入 `UserContext`，请求结束后清理 ThreadLocal。
4. Feign 请求通过 `DefaultFeignConfig` 透传用户上下文；点评内容需要用户资料时调用 `UserClient`。

## 核心业务边界

- 商品订单由 `trade-service` 创建，调用商品服务校验商品和库存、调用购物车服务清理购物车；支付模块处理支付单和结果通知。
- 本地生活优惠券由 `local-life-service` 管理活动和秒杀订单。秒杀入口基于当前统一用户 ID 获取 Redisson 锁；事务中检查活动时间、执行 `stock > 0` 条件扣减并插入订单。数据库 `(user_id, voucher_id)` 唯一索引是跨进程的最终去重约束。
- 本地生活券订单和商城 `Order` 保持各自的业务聚合。两类订单共用 `pay-service` 余额支付：支付服务通过 Feign 查询券订单归属、金额和状态，成功后用 RabbitMQ 的 `voucher.pay.success` 路由通知本地生活服务更新券订单。支付通知是异步的，Seata 仍未启用；当前没有跨数据库原子提交或消息发件箱保证。

## 运行时依赖

| 能力 | 技术 | 用途 |
|---|---|---|
| 服务发现/配置 | Nacos | 服务注册发现及共享配置 |
| 服务间调用 | OpenFeign | 用户资料与服务 API 调用 |
| 缓存/关系数据 | Redis | 验证码、缓存、Feed、签到、ID 生成 |
| 秒杀互斥 | Redisson | 同一用户并发请求串行化 |
| 持久化 | MySQL + MyBatis-Plus | 用户、商品、订单、点评业务 |
| 异步消息 | RabbitMQ | 电商支付结果通知等已有服务流程 |

具体运行效果需要依赖服务、数据库脚本和 Nacos 配置共同验证；Maven 编译通过仅证明源码能够构建。
