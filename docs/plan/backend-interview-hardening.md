# Java 后端项目面试追问补强计划

更新时间：2026-10-24。本文规划 Redis 锁、Seata 支付回滚、多用户秒杀竞争和 RabbitMQ 消费失败处理四项工作。当前代码已经具备 outbox 重试/对账及券取消、核销、退款闭环；本计划补强边界正确性和可复现的故障证据，不把待实现项提前写成项目成果。

## 目标

- 修复缓存重建锁在竞争场景下可能误删其他线程锁的问题，并为热点 Key 重建提供并发证据。
- 验证 Seata 是否能在用户余额已扣、支付单已更新、outbox 写入失败时回滚所有分支。
- 用多个用户同时竞争有限库存，证明数据库条件扣减和唯一约束的实际效果。
- 为消费者异常配置有限重试和死信队列，避免毒消息无限重投或静默丢失。
- 每项都保存命令、环境、通过条件和 SQL/队列/服务日志等证据，作为面试追问和简历表述依据。

## 当前代码基线与风险

| 工作项 | 当前发现 | 风险 |
|---|---|---|
| 缓存互斥重建 | `CacheClient.queryShopWithMutex` 未获得锁时递归等待，但外层 `finally` 仍调用无条件 `unlock`；等待者可能删掉持锁者的 Key。等待使用递归，长时间竞争会增加调用栈和请求线程占用。 | 热点 Key 竞争时互斥失效，可能击穿数据库。 |
| 逻辑过期 | `setWithLogicalExpire` 构造了 `RedisData`，写入时却序列化原始对象；代码库中暂未发现该方法的调用路径。 | 不能把逻辑过期作为已经生效的能力来讲。 |
| 支付事务 | 余额扣减、支付状态和 outbox 插入位于 `@GlobalTransactional` 方法中，成功链路已走通；目前没有在支付中途制造分支失败并验证全局回滚的专门用例。 | 代码注解不能替代跨服务回滚证据。 |
| 秒杀竞争 | Redisson 按用户加锁，库存由 MySQL `stock > 0` 条件更新，订单有 `(user_id, voucher_id)` 唯一索引；现有并发测试聚焦同一个用户。 | 缺少多个用户同时竞争有限库存的证据。 |
| RabbitMQ 消费失败 | 消费者方法调用状态更新，业务状态更新具有幂等条件；当前没有明确的有限重试、死信队列及人工重放流程。 | 毒消息可能反复 requeue，排查与恢复路径不清楚。 |

## 分阶段实施

### 阶段一：修复 Redis 锁并补热点 Key 并发测试（最高优先级）

**实施方案**

1. 重构 `CacheClient.queryShopWithMutex`：移除递归和无锁释放；仅在明确获取锁后进入释放逻辑，等待使用有上限的循环或 Redisson `RLock` 等待接口，并正确处理中断。
2. 锁释放必须具备持有者校验且原子执行。优先复用项目已引入的 Redisson；若保留 `SET NX` 实现，则为每次获取生成唯一 token，并用 Lua compare-and-delete 解锁，避免“先 GET 再 DEL”的竞态。
3. 修复空值缓存逻辑：数据库无记录时写入带 TTL 的空值标记；数据库有记录时只写一次缓存。明确热点 Key 锁超时后的降级策略，避免无限递归等待。
4. 修复逻辑过期序列化，并决定是否真正接入。若本轮不实现逻辑过期查询与后台刷新，则删除未使用的误导性方法，文档只声明已验证的缓存策略。
5. 检查并统一 `SimpleRedisLock`：原子校验并释放锁，或移除无人调用的旧实现，避免保留另一份有风险的锁代码。

**验收测试**

- 对空缓存的同一商户详情发起 50–100 个并发请求，响应全部正确，无请求长时间挂起。
- 通过测试计数器或 SQL 统计确认重建期间数据库回源只有少量次数（预期一个持锁回源；如果使用短锁超时，需在用例里说明允许的边界）。
- 持锁请求尚未释放时，等待请求不得删除锁；持锁请求完成后，锁 Key 最终释放或过期。
- 对不存在的商户并发请求，空值缓存按 TTL 生效，不形成持续数据库回源。
- 测试等待超时、Redis 短暂异常和线程中断，确保线程退出并保留中断语义。

**交付**：锁实现、缓存并发测试脚本或集成测试、结果记录、修订后的缓存设计说明。

### 阶段二：支付 Seata 回滚故障注入

**实施方案**

1. 新增仅限隔离测试环境的故障注入用例，不新增公开业务接口。首选通过测试夹具制造确定性失败：对待支付单预置同 `pay_order_id` 的 outbox 唯一键记录，使余额扣减和支付单状态更新完成后，真实 outbox 插入触发唯一键冲突。
2. 故障用例先读取 Jack 余额、支付单状态、业务订单状态和 outbox 状态；触发失败后重新读取并比较。测试结束清除夹具，随后正常支付同一订单，确认可恢复。
3. 核实 Seata XID 是否经 Feign 从支付服务传至用户服务，确认用户扣款、支付库状态更新及 outbox JDBC 插入都参与同一个全局事务。
4. 增加第二个失败点（可选）：在 outbox 写入成功后、全局提交前抛出测试异常，验证支付库和用户库均回滚，且没有可被发布器消费的提交事件。

**验收测试**

- 注入失败时 HTTP 返回业务错误，用户余额与支付前相同。
- 支付单仍为待支付，测试夹具之外没有新的 outbox 事件，业务订单仍未支付，RabbitMQ 没有收到有效支付通知。
- Seata TC 日志能关联到该 XID 并显示全局回滚；三库 SQL 快照与回滚前一致。
- 清理故障夹具后，对同一支付单重新支付成功，余额仅扣一次、outbox 仅有一条有效事件、业务订单最终进入已支付状态。

**交付**：可重复执行的 `test_payment_seata_rollback` 用例、SQL 前后快照、XID/TC 日志、失败恢复记录。

### 阶段三：多用户秒杀库存竞争

**实施方案**

1. 测试脚本在隔离库准备多个独立用户或复用专用测试账号，登录后为每个并发请求使用独立会话和 JWT。
2. 创建库存为 1、10、50 的临时活动；分别让 20、100、200 个不同用户同时抢购。通过屏障同步发起时间，记录成功、库存不足、重复订单及异常响应。
3. 每轮结束通过 SQL 核验券库存、订单总数和用户维度重复订单；脚本下架活动并保留可清理的测试数据标记。
4. 重复多轮并覆盖相同用户重复点击与不同用户争库存两类竞争，分别验证 Redisson 用户锁和数据库条件更新/唯一索引的职责。

**验收测试**

- 成功订单数不超过初始库存；最终库存不小于 0。
- 每个用户对同一活动最多一张订单；不存在“返回成功但没有订单”或“扣库存但订单未落库”的残留。
- 库存耗尽后继续请求只得到业务失败，不出现负库存。
- 报告只描述请求数、并发模型、成功数和数据校验，不把本地竞争测试包装成生产吞吐指标。

**交付**：多用户并发脚本、每轮 CSV/JSON 结果和订单/库存 SQL 核验记录。

### 阶段四：RabbitMQ 消费重试与死信处理

**实施方案**

1. 在交易和本地生活消费者统一配置有限次数的指数退避重试，随后拒绝并路由到持久化 DLX/DLQ；避免默认无限 requeue。将重试次数、初始间隔、最大间隔配置化。
2. 为支付通知增加稳定事件标识（outbox event ID）并作为 AMQP message ID 或 header 传递；保留订单 ID，便于日志、死信排查和重放关联。
3. 消费者保留当前状态条件更新的幂等行为。定义死信查看、确认原因、修复后重放的本地操作步骤；重放只能使用原事件标识，不能重复扣款。
4. 为队列和 DLQ 建立明确命名与拓扑定义，并记录消息持久化、队列 durable、publisher confirm 与 consumer ack 的边界；不要把 publisher confirm 说成消费者已处理成功。

**验收测试**

- 对消费端注入确定性异常，观察有限重试次数和间隔；消息最终进入 DLQ，主队列不会无限增长或空转。
- 修复异常后从 DLQ 重放，业务订单更新成功；重复投递同一事件不产生重复支付、重复退款或额外状态副作用。
- Broker 或消费者重启后，持久化主队列与死信仍可读取，重放流程可复现。
- 记录队列深度、DLQ 数量和错误日志；如暂不接监控平台，至少提供命令行核验步骤。

**交付**：Rabbit 拓扑和消费者策略、毒消息故障注入脚本、DLQ 重放步骤及结果。

## 执行顺序与发布门槛

1. 先修 Redis 锁并补测试，避免已知并发风险影响后续秒杀实验。
2. 做 Seata 支付回滚注入，确认跨服务事务边界与 outbox 原子性。
3. 做多用户库存竞争，确认秒杀数据库约束在真实并发下有效。
4. 最后增加消费者重试和 DLQ，补齐从生产、投递到消费失败恢复的消息闭环。
5. 每个阶段单独提交；完整执行 Maven 构建、接口联调、故障注入脚本和前端冒烟，再更新 [`docs/evaluation.md`](../evaluation.md)、[`docs/verification/api-test-matrix.md`](../verification/api-test-matrix.md) 与简历表述。

## 暂不宣称的结果

在相应阶段通过之前，不宣称缓存互斥已可靠、多用户高并发已证明不超卖、Seata 支付链已完成失败回滚验证，或 RabbitMQ 消费端具备死信与人工恢复能力。完成全部阶段也只证明本机隔离环境中的这些场景通过，不等同于生产可用性认证。
